# 数据从哪来：WPS 升级了怎么办

`~/.config/Kingsoft/Office.conf` 是 **WPS 内部私有格式，不是公开接口**。它哪天把
`RecentFiles` 改个名、把转义换个写法，只认键名的解析就会静默返回空列表 —— 这是
这类工具的先天风险。

所以最近文档分三层取，任何一层有收获就用：

| 层 | 做法 | 抗什么 |
|---|---|---|
| 1. 结构化 | 按键名 `wps\RecentFiles\files\N\path=` 解析 | 正常情况，能拿到序号 |
| 2. 通用扫描 | 同一个文件里，凡是「值像被转义的绝对路径、且指向真实文档」的键值对全部收下 | **键名/层级被改名** |
| 3. 云目录补扫 | 扫 `~/文档/WPS Cloud Files`，把近 30 天动过的文档补进来（按 mtime 封顶 200 条） | **WPS 压根不写记录**的云端文档，见下文 |
| 4. 兜底源 | 主源一条都读不出时，改用 GTK 的 `recently-used.xbel` 和云目录里最近改过的文档 | 配置彻底读不出来 |

配置文件本身也有兜底：`~/.config/Kingsoft/Office.conf`、`~/.config/kingsoft/Office.conf`、
`~/.config/Kingsoft/office.conf` 都试。

**最坏情况**（WPS 把值改成加密/base64，连路径形态都没有）三层都无能为力，但这时
不会静默：状态栏会说「WPS 的配置里没解析出任何文档路径 —— 多半是 WPS 升级后改了
格式」，并把 tooltip 里的明细和 `wps-copy --doctor` 指给你。

判断当前机器到底走的哪一层：

```sh
wps-copy --doctor
```

它会打印会话类型（X11 / Wayland）、依赖、配置文件的命中数
（`结构化 35 条 / 通用扫描 35 条`）、兜底源是否存在、三个后台进程的状态。把这个
输出贴到 issue 里，基本能定位所有「列表是空的」问题。

## 解析里的那个坑

`Office.conf` 里的路径用 `\x` + **2~4 位**十六进制转义。ASCII 字符也会被转义，比如
文件名里的 `2026` 写成 `\x32\x30\x32\x36`。

早期按「定长 4 位」解析会把 `\x32\x30` 吃成一个字符 `0x3230`，整条路径变乱码、
文件被判为不存在而被过滤掉 —— 表现就是「名字带数字的文件在列表里看不到」。现在按
「最多 4 位、遇非十六进制字符即停」解析。

`src/wpsclip/recent.py` 里那个 `\x` 变长转义正则（`{1,4}`、遇非十六进制即停）是全
项目最容易踩坑的一行。动它之前先读 `tests/test_recent.py` —— 里面每条用例都对应
一个真实踩过的坑。

## 顺序从哪来：Sequence，不是文件修改时间

`files\N\path` 里的 N 只是**该类型内部的位次** —— `wps`、`et`、`pdf` 各有一套，
都从 1 开始，跨类型没法比。真正的顺序在另一个地方：

```
wps\RecentFiles\Sequence\home\shuai\%U6587%U6863\a.docx=1792109632
```

右边是 **Unix 秒级的打开时间**，左边是路径，用的是另一套编码：

- `%UXXXX` 表示一个 UTF-16 码点（`%U6587` = 文，`%U6863` = 档）
- 其余是标准百分号编码（`%20` = 空格）
- 键里没有前导斜杠、用反斜杠当分隔符

同一个文件被多个产品段打开过就会有多条记录，取最新那次。

**为什么不能用 `st_mtime`**：1.11.0 及以前就是这么做的，于是「打开一份排在后面的
老文档、一个字都不改」不会挪到前面 —— WPS 那边已经排第一，这边纹丝不动。
`atime` 也不行：relatime 规则下一天最多更新一次，实测顺序错乱得厉害。

现在的排序规则（`recent.collect_meta`）：

1. 有打开记录的整批排在前面（本地看 Sequence，云端见下一节），批内按打开时间倒序；
2. 没有记录的（兜底数据源、老版本配置）按 `st_mtime` 倒序排在后面。

第 1 条那个「整批」不能省：否则一个刚被别的软件改过、WPS 从没打开过的文件，
会压过半分钟前刚打开的那份。

想确认自己机器上读到了多少条：

```sh
wps-copy --doctor      # 看「打开时间 17 条」
```

## 云文档

WPS 云文档在本地通常留有一份缓存副本，这些也会出现在列表里，来源列标记为「云端」。
纯在线的、本地没有任何落盘文件的文档无法复制 —— 没有文件对象就没有可粘贴的东西。

**云端文档的打开记录在另一处**，和本地文档的 `RecentFiles` 完全分家：

```
plugins\officespace\usercenter\<用户>\openfilelist\3\path=/home/shuai/\x6587\x6863/WPS Cloud Files/...
plugins\officespace\usercenter\<用户>\openfilelist\3\localpath=...
```

这里只有位次（1 最旧、往后越新）和一句 `recordtime=<日期>`，**没有秒级时间**。
更麻烦的是云端缓存的路径里带一段随同步变化的哈希：

```
WPS Cloud Files/.<账号>/cachedata/<哈希>/<文件名>.docx
```

哈希一变，Sequence 里记的那条就指向一个早就不存在的旧缓存，而真正能打开的那份
只在 `openfilelist` 里。所以云端文档的打开时间按这个顺序补
（`recent.parse_open_times`）：

1. `Sequence` 里同名云文档的记录 —— 缓存换了哈希，文件名还能对上；
2. 本地缓存的 `mtime` —— WPS 打开云端文档时会写这份缓存。

少了这一层，云端文档拿不到打开时间，会被「有 Sequence 记录的整批在前」这个档位
压到最后：托盘「最近 5 个」轮不到它，快捷键复制也永远复制不到刚打开的云端文档。
`wps-copy --doctor` 会多打一行「其中云端文档 N 条」，就是这层补上的数量。

**有些云端文档连 `openfilelist` 都不进。** 典型是「另存为到团队文档」之后接着
编辑：WPS 只在云同步目录里落一个文件，`RecentFiles`、`openfilelist` 一处记录都
没有 —— 它的最近列表是**从云端拉的**，本地不留痕。这时配置里再怎么解析都找不到
它，只能靠文件本身：

```
WPS Cloud Files/<账号>/团队文档/<部门>/<分类>/<子类>/<文件名>.docx
                                  ↑ mtime = WPS 最后一次写它
```

所以 `recent.scan_cloud_docs()` 会把云同步目录里**近 30 天**动过的文档补进来
（按 mtime 取最近的 200 个，跳过隐藏目录、非文档）。排序上它和「有打开记录的」
算同一档：云目录由 WPS 独占写入，这里的 mtime 就是可信的「最近动过」证据，
不像别处可能被下载工具、编辑器顺手改掉。

阈值和条数在 `recent.py` 的 `CLOUD_RECENT_DAYS` / `CLOUD_SCAN_MAX`。目录很大、
列表被灌满时可以调小；云文档同步到别的路径时，把路径加进 `CLOUD_DIRS`。

还有一种情况仍然无解：WPS 里最新那条是云端文档、本地还没有缓存副本（比如刚清过
缓存）。它没有文件可复制，快捷键会退而复制下一个，并在通知里说明
「更近的「xxx」本地没有副本」—— 在 WPS 里打开一次让它落盘即可。
