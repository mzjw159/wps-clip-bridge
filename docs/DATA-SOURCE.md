# 数据从哪来：WPS 升级了怎么办

`~/.config/Kingsoft/Office.conf` 是 **WPS 内部私有格式，不是公开接口**。它哪天把
`RecentFiles` 改个名、把转义换个写法，只认键名的解析就会静默返回空列表 —— 这是
这类工具的先天风险。

所以最近文档分三层取，任何一层有收获就用：

| 层 | 做法 | 抗什么 |
|---|---|---|
| 1. 结构化 | 按键名 `wps\RecentFiles\files\N\path=` 解析 | 正常情况，能拿到序号 |
| 2. 通用扫描 | 同一个文件里，凡是「值像被转义的绝对路径、且指向真实文档」的键值对全部收下 | **键名/层级被改名** |
| 3. 兜底源 | 主源一条都读不出时，改用 GTK 的 `recently-used.xbel` 和 `~/文档/WPS Cloud Files` 里最近改过的文档 | 配置彻底读不出来 |

配置文件本身也有兜底：`~/.config/Kingsoft/Office.conf`、`~/.config/kingsoft/Office.conf`、
`~/.config/Kingsoft/office.conf` 都试。

**最坏情况**（WPS 把值改成加密/base64，连路径形态都没有）三层都无能为力，但这时
不会静默：状态栏会说「WPS 的配置里没解析出任何文档路径 —— 多半是 WPS 升级后改了
格式」，并把 tooltip 里的明细和 `wps-copy --doctor` 指给你。

判断当前机器到底走的哪一层：

```sh
wps-copy --doctor
```

它会打印会话类型（X11 / Wayland）、依赖、配置文件的命中数
（`结构化 35 条 / 通用扫描 35 条`）、兜底源是否存在、三个后台进程的状态。把这个
输出贴到 issue 里，基本能定位所有「列表是空的」问题。

## 解析里的那个坑

`Office.conf` 里的路径用 `\x` + **2~4 位**十六进制转义。ASCII 字符也会被转义，比如
文件名里的 `2026` 写成 `\x32\x30\x32\x36`。

早期按「定长 4 位」解析会把 `\x32\x30` 吃成一个字符 `0x3230`，整条路径变乱码、
文件被判为不存在而被过滤掉 —— 表现就是「名字带数字的文件在列表里看不到」。现在按
「最多 4 位、遇非十六进制字符即停」解析。

`src/wpsclip/recent.py` 里那个 `\x` 变长转义正则（`{1,4}`、遇非十六进制即停）是全
项目最容易踩坑的一行。动它之前先读 `tests/test_recent.py` —— 里面每条用例都对应
一个真实踩过的坑。

## 云文档

WPS 云文档在本地通常留有一份缓存副本，这些也会出现在列表里，类型列标记为「云」。
纯在线的、本地没有任何落盘文件的文档无法复制 —— 没有文件对象就没有可粘贴的东西。
